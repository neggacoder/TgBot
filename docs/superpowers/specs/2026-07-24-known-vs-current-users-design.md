# «Нью» — разделение known_users (история) и current_users (сейчас в чате)

Дата: 2026-07-24
Статус: одобрено пользователем в чате, ожидает записи в план реализации.

## Контекст

Третий подпроект в очереди (после «Награды — пороги по ролям» и «Предложить
действие» — см. соседние спеки в этой же директории). Следующие в очереди —
опция «все» в порогах наград и выдача награды всем участникам чата разом
(отдельные спеки, после этого подпроекта).

Баг: бот считает вернувшегося в чат участника «новым», хотя он уже был тут
раньше — просто вышел и зашёл снова. Проявляется в командах «Олды»/«Новички»/
«нью {период}», в правиле рестов «🌱 Стаж новичка», в списке молчунов.

Корень бага (найден исследованием): понятие «стаж/дата первого появления»
(`known_users.first_seen_at`) и понятие «кого бот сейчас видит в чате»
физически хранятся в ОДНОЙ таблице `known_users` (`schema.sql:32-40`,
per-chat, PK `(chat_id, user_id)`). При выходе участника `handle_member_left`
(`bot.py:359-397`) вызывает `db.delete_known_user(chat_id, user.id)`
(`bot.py:382`) — строка физически удаляется, `first_seen_at` теряется. При
повторном входе `upsert_known_user` (`db.py:1435-1452`) делает свежий
`INSERT`, `first_seen_at` = `DEFAULT CURRENT_TIMESTAMP` = «сейчас». Вся
логика, читающая `first_seen_at`, честно видит «человек тут первый день».

Показательная деталь: у `message_stats` тоже есть `first_seen_at`
(`schema.sql:216-224`), но она НЕ удаляется при выходе (только целиком по
чату, вручную, `reset_message_stats`) — то есть в кодовой базе уже есть
пример живущего дольше `first_seen_at`, просто на него не завязана логика
новизны.

Отдельной таблицы «кто сейчас реально в чате» в проекте нет — `known_users`
исполняет две несовместимые роли одновременно: (а) кэш «кого бот видел» для
разных пикеров, (б) источник истины про дату первого появления. Разделение
этих двух ролей — и есть исправление бага.

## Требование

- Никогда не удалять строки из `known_users` при выходе участника — вопросы
  про новизну/стаж (Олды/Новички/«нью»/рест-правило «Стаж новичка»/молчуны/
  «в каких чатах видел») всегда смотрят в `known_users`, независимо от того,
  состоит ли человек в чате прямо сейчас.
- Новая таблица `current_users` — те, кто прямо сейчас состоит в чате.
  Строка появляется при входе (и при любой активности), исчезает при выходе.
- Вопросы про «кто прямо сейчас в чате» смотрят в `current_users`.

## Дизайн

### 1. Схема БД (`db.py`, новый `ensure_current_users_table`)

```sql
CREATE TABLE IF NOT EXISTS current_users (
    chat_id BIGINT NOT NULL,
    user_id BIGINT NOT NULL,
    full_name VARCHAR(255) NOT NULL,
    username VARCHAR(64) NULL,
    last_seen_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    PRIMARY KEY (chat_id, user_id),
    INDEX idx_current_users_seen (chat_id, last_seen_at DESC)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

Без `first_seen_at`/`invited_by` — это исторические поля, `current_users`
их не хранит. Схема и CRUD-паттерн (`INSERT ... ON DUPLICATE KEY UPDATE`,
`DELETE ... WHERE chat_id=%s AND user_id=%s`) — прямая копия `known_users`
(`db.py:1435-1459`).

### 2. Заполнение — везде, где сейчас пишется `known_users` при «человек тут»

Четыре места вызывают `db.upsert_known_user(...)` (`bot.py`, grep
подтвердил ровно эти 4 вызова):

- `MessageCounterMiddleware` (`bot.py:223-228`) — на каждое сообщение от
  не-бота в группе/супергруппе. Рядом добавляется
  `await db.upsert_current_user(event.chat.id, event.from_user.id,
  event.from_user.full_name or str(event.from_user.id),
  event.from_user.username)`. Это даёт самовосстановление: участники,
  вступившие ДО деплоя фикса (и поэтому никогда не попадавшие в
  `current_users` через событие входа), появятся там сами по себе, как
  только напишут хоть одно сообщение — не нужно полагаться только на
  бэкафилл (п.5).
- `handle_member_joined` (`bot.py:290-356`, вызов `upsert_known_user` на
  строке 297) — рядом добавляется тот же `upsert_current_user`.
- `sync_known_admins` (`bot.py:3826-3845`, вызов на строке 3839) — рядом
  добавляется `upsert_current_user` (админов Telegram отдаёт всегда, даже
  молчаливых — источник появления в `current_users` без единого
  сообщения).
- `complaint_roster_add_name` (`bot.py:4258-4274`, вызов на строке 4274) —
  **НЕ трогаем**. Это ручное добавление админом произвольного человека в
  ростер целей жалобы (по пересланному сообщению или голому ID + свой
  подписанный текст, например «Соседка сверху» — судя по подсказке в UI,
  рассчитано и на людей, не обязательно состоящих в чате). Такой человек не
  обязательно «сейчас в чате» — в `current_users` его добавлять неверно.

### 3. Очистка — единственное место, и это единственное исправление бага

`handle_member_left` (`bot.py:359-397`), строка 382:
```python
await db.delete_known_user(chat_id, user.id)
```
заменяется на:
```python
await db.delete_current_user(chat_id, user.id)
```
Всё остальное в `handle_member_left` (снятие подписок/репутации/данных
звонков, освобождение роли) не меняется — эти вещи и раньше корректно
относились к «человек больше не тут», просто были случайно завязаны на ту
же таблицу, что и стаж.

`complaint_roster_delete_confirm` (`bot.py:4303-4319`, ручное удаление
записи из ростера жалоб администратором) по-прежнему вызывает
`db.delete_known_user` — это отдельное осознанное действие админа над
ростером жалоб, не связано с выходом из чата, не трогаем.

### 4. Кто на что переключается (консьюмеры `known_users`)

**Остаются на `known_users` без изменений** (все читают `first_seen_at`
или намеренно нужен весь известный список, а не только текущий):
- «Олды»/«Новички» (`cmd_oldtimers`, `bot.py:14957-14998`)
- «нью {период}» (`cmd_new_members`, `bot.py:15001-15043`,
  `db.list_new_members_since`)
- Рест-правило «🌱 Стаж новичка» (`db.get_member_first_seen`,
  `db.py:2287-2295`)
- «Молчуны, вступившие до …» (`db.list_silent`)
- «В каких чатах бот видел» (`db.list_user_chats`)
- Выбор цели жалобы — и авто-список (`complaint_picker_page`,
  `bot.py:3848-3882`, использует `db.list_known_users`/
  `db.search_known_users`), и ручной ростер (`complaint_roster_add_id`/
  `complaint_roster_add_name`) — **осознанно широкий список**, специально
  допускает не-участников чата (см. п.2). Первоначально в брейншторминге
  планировалось перевести это на `current_users` — решение отменено после
  того, как выяснилось, что ручное добавление не-участников — это
  намеренная возможность, а не побочный эффект.
- `get_last_seen_map` (онлайн-статус) — читает `last_seen_at` из
  `known_users`, не связано с проверкой присутствия, не трогаем.

**Переходят на `current_users`:**
- «участники без ролей» (`cmd_members_without_role`, `bot.py:5329-5338`) —
  `db.list_known_users_without_role` → новая `db.list_current_users_without_role`
  (тот же SQL-паттерн, что и оригинал, `db.py`, но `FROM current_users`
  вместо `FROM known_users`). Не имеет смысла предлагать назначить роль
  тому, кто уже вышел.
- Вкладка «Чаты и люди» на сайте, эндпоинт `GET /api/members`
  (`webpanel/app.py:658-697`) — `db.list_known_users_with_counts` → новая
  `db.list_current_users_with_counts` (тот же JOIN с `message_stats` по
  `(chat_id, user_id)`, но по `current_users`).

**Вне рамок этой задачи** (замечено при исследовании, но не в этом
запросе — не трогаем): `GET /api/member/chat-members`
(`webpanel/app.py:2477-2495`, поиск «на ком жениться» в РП-фиче) тоже
читает `known_users` и в теории мог бы предлагать уже вышедших из чата — но
это отдельный, не запрошенный сейчас вопрос.

### 5. Бэкафилл при деплое

Разовая миграция данных — новая функция `db.backfill_current_users_from_known_users()`:
```sql
INSERT IGNORE INTO current_users (chat_id, user_id, full_name, username, last_seen_at)
SELECT chat_id, user_id, full_name, username, last_seen_at FROM known_users
```
с тем же идиомом «выполнить только если таблица-назначение пуста» (`COUNT(*)`
guard), что уже используется в проекте для `seed_rp_actions_if_empty` и
аналогичных (`db.py:3155-3167`) — вызывается один раз в `main()`, сразу
после `ensure_current_users_table()`.

Обоснование: бот не может запросить у Telegram полный список участников
обычной группы (Bot API этого не отдаёт), поэтому нет другого источника
истины «кто сейчас в чате» на момент деплоя, кроме предположения «все, кого
`known_users` считает известными прямо сейчас — предположительно ещё в
чате». Неточность (кто-то мог выйти до деплоя и повиснуть как «ложно
текущий») со временем самоисправится через реальные события выхода.

  `GET /api/members` использует `list_current_users_with_counts`.
