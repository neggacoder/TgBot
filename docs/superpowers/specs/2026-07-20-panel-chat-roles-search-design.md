# Поиск по ролям чата в веб-панели

Дата: 2026-07-20

## Задача

В панели появляется страница «Роли чата» — поиск и просмотр игровых ролей
участников (`chat_roles`): какие роли есть, кто их носит, какие свободны, какие
забронированы и до какого момента.

Только чтение. Занимать, выдавать, бронировать и удалять роли по-прежнему можно
из бота — панель ничего в игровой механике не меняет.

## Что важно не перепутать

В панели уже есть `webpanel/roles.py` и `GET /api/roles` — это **уровни прав**
(владелец, старший, админ, модератор, участник). Роли чата — другая сущность с
тем же словом в названии. Поэтому новый эндпоинт называется `/api/chat-roles`,
а модуль уровней не трогаем: склеивать их в один путь — верный способ однажды
показать модератора там, где ждали «Аскэ Лэнгли».

## 1. Данные

Роли лежат в `chat_roles` (создаётся в `db.ensure_chat_roles_table`,
`db.py:2231`): `id`, `name`, `category`, `status ENUM('free','taken','reserved')`,
`holder_user_id`, `reserved_user_id`, `reserved_at`, `approved`.

Имён людей там нет — только `user_id`, имена живут в `known_users`. Поэтому
нужна одна новая функция:

```python
async def search_chat_roles(
    chat_id, *, q=None, status=None, category=None, limit=100, offset=0
) -> tuple[list[dict], int]
```

- два `LEFT JOIN known_users` — держатель и забронировавший (по `chat_id` тоже,
  иначе подтянется тёзка из другого чата);
- `q` ищет по названию роли, категории, полному имени и username обоих людей —
  через `LIKE %q%`, регистронезависимо. Один запрос вместо «найди роль» и
  «найди, что у человека»: в панели это одно поле поиска;
- `status` — один из `free`/`taken`/`reserved`/`pending`. Первые три ложатся в
  `status`, `pending` — это `approved = FALSE` (заявка на модерации), поэтому
  без фильтра выдаём только одобренные, как `list_roles`;
- сортировка `category IS NULL, category, name` — та же, что в боте, чтобы
  порядок в панели и в чате совпадал;
- возвращает строки и общее число (для «показано N из M»).

Ещё две функции — для того, что не должно зависеть от текущего фильтра:

```python
async def count_chat_roles_by_status(chat_id) -> dict[str, int]
async def list_role_categories(chat_id) -> list[str]
```

Счётчики на чипах и список категорий считаются по всему чату, а не по выборке:
иначе, отфильтровав список до одной роли, человек увидел бы «свободных: 0» и
пустой список категорий — то есть цифры, описывающие его же фильтр, а не чат.

Список статусов для фильтра живёт в `db.ROLE_SEARCH_STATUSES` — там же, где
запросы, которые его понимают; панель проверяет параметр по нему.

## 2. API

`GET /api/chat-roles?chat_id=&q=&status=&category=&limit=&offset=`

Доступ — `require_user`, как у `/api/members`: это просмотр, не управление.

`status` проверяется по белому списку, иначе `HTTPException(400)` — как уже
сделано для `role` в `/api/members`. `limit` ограничен сверху (200).

Ответ:

```json
{
  "roles": [{
    "id": 42, "name": "...", "category": "...", "status": "reserved",
    "holder": {"user_id": 1, "full_name": "...", "username": "..."} | null,
    "reserved_by": {...} | null,
    "reserved_at": "...", "reserve_expires_at": "...",
    "approved": true
  }],
  "total": 137,
  "counts": {"free": 90, "taken": 40, "reserved": 5, "pending": 2},
  "categories": ["..."],
  "reserve_timeout_hours": 72
}
```

Пустой `status` — это «фильтра нет», а не ошибка: фронтенд шлёт `status=` при
сбросе чипа. Отвергается только непустое значение вне списка.

`reserve_expires_at` считается как `reserved_at + role_reserve_timeout_hours`,
где часы берутся из `settings.role_reserve_timeout_hours` с тем же дефолтом,
что у бота (`ROLE_RESERVE_TIMEOUT_HOURS`, 72). Читаем ту же настройку намеренно:
показывать срок, которого бот не придерживается, хуже, чем не показывать срок.

## 3. Интерфейс

Новая вкладка «Роли чата» в боковом меню, между «Чаты и люди» и «Модерация».

**Только SVG-иконки, никаких эмодзи** — как и во всей панели. В спрайт
(`webpanel/static/index.html`) добавляются недостающие символы в том же
stroke-стиле, `viewBox="0 0 24 24"`: `ic-mask` (вкладка), `ic-clock` (срок
брони), `ic-user` (держатель). Остальное берётся из готовых (`ic-search`,
`ic-check`, `ic-alert`, `ic-empty`).

Экран: поле поиска, ряд чипов-фильтров со счётчиками (все / свободные / занятые
/ забронированные / на модерации), под ними — список ролей, сгруппированный по
категориям. У занятой роли — держатель с аватаркой (`avatar()`), у
забронированной — кто забронировал и когда бронь сгорит, у заявки — пометка
«на модерации».

Поиск с задержкой ввода (как в существующих списках панели), пустой результат —
через `empty()`.

## 4. Тесты

`tests/test_panel_chat_roles.py` — по образцу `test_panel_roles.py`, с
подменёнными функциями `db`:

- поиск находит по названию, по категории, по имени держателя и по username;
- фильтр по каждому статусу отдаёт только его роли;
- `pending` показывает неодобренные, а без фильтра их не видно;
- неизвестный статус → 400;
- роль без держателя и без брони не роняет ответ (`holder: null`);
- у брони посчитан `reserve_expires_at` по настройке, а не по «зашитым» 72 ч.

## Границы

- Только чтение: никаких действий над ролями из панели.
- Истории («кто носил роль раньше») нет — структурированного лога ролей в базе
  не существует, а восстанавливать её парсингом текстовых `details` из общего
  журнала значит показывать догадки как факты.
- Поиск по ролям в самом боте (команда «роль найти») не добавляется, хотя
  `search_chat_roles` для него уже подойдёт.
- `db.py` в этой работе получает только новые функции; существующие запросы
  ролей не переписываются.
