# Варны по умолчанию 7 дней + правила и шаблон реста

Дата: 2026-07-20

## Задача

1. Варн без явного срока выдаётся на 7 дней (сейчас — 30).
2. У реста появляются настраиваемые правила (максимум две недели, пауза между
   рестами, запрет для новичков, окно перед чисткой) — бот их реально проверяет,
   а не только показывает.
3. Текст-памятка о ресте с подставляемыми полями (дата начала, дата окончания,
   причина) показывается пользователю при подаче заявки и админам при одобрении.
4. Всё настраивается и через бот, и через веб-панель.

## 1. Варны

`bot.py`: `WARN_DEFAULT_DURATION = timedelta(days=7)`. Явный срок в команде
(`варн 3д спам`) по-прежнему перекрывает дефолт. Комментарий у константы и
упоминание в docstring `db.add_warn` приводятся в соответствие.

## 2. Модуль `rest_rules.py`

`bot.py` уже около мегабайта, поэтому логика реста живёт в отдельном модуле
чистыми функциями — без обращений к БД и Telegram, значит её можно тестировать
напрямую.

```python
DEFAULT_REST_TEMPLATE: str      # текст-памятка с плейсхолдерами
REST_PLACEHOLDERS: tuple[str]   # список имён для подсказки админу

def render_rest_template(template, *, start, end, reason, member, duration_text) -> str
def check_rest_rules(*, now, duration, first_seen_at, last_rest_end, limits) -> str | None
```

`render_rest_template` подставляет русские плейсхолдеры и экранирует причину и
имя участника (в Telegram уходит `parse_mode=HTML`). Неизвестные фигурные скобки
в пользовательском шаблоне не должны ронять рендер — подстановка идёт заменой по
известным ключам, а не `str.format`.

Плейсхолдеры: `{дата_начала}`, `{дата_окончания}`, `{причина}`, `{участник}`,
`{срок}`.

`check_rest_rules` возвращает готовый текст отказа (или `None`, если всё в
порядке) и проверяет по порядку:

1. `duration` больше `rest_max_days` — отказ с указанием максимума;
2. стаж в чате (`now - first_seen_at`) меньше `rest_min_member_days` — отказ с
   датой, начиная с которой рест станет доступен;
3. предыдущий рест закончился меньше `rest_cooldown_days` назад — отказ с датой
   доступности следующего;
4. задана `rest_cleanup_date`, и `now` попадает в окно
   `[cleanup_date - rest_cleanup_block_days, cleanup_date]` — отказ.

Правила действуют одинаково для всех, включая администраторов и владельца.
Отсутствующие данные (нет `first_seen_at`, нет прошлого реста, не задана дата
чистки) соответствующую проверку пропускают.

## 3. Настройки

Хранятся в существующей таблице настроек (`db.save_setting` / `settings`), как
`welcome_message`:

| ключ | дефолт | смысл |
|---|---|---|
| `rest_rules_template` | `DEFAULT_REST_TEMPLATE` | текст-памятка |
| `rest_max_days` | 14 | максимальная длительность одного реста |
| `rest_cooldown_days` | 14 | пауза после окончания предыдущего реста |
| `rest_min_member_days` | 14 | минимальный стаж в чате |
| `rest_cleanup_date` | пусто | дата ближайшей чистки, `ДД.ММ.ГГГГ` |
| `rest_cleanup_block_days` | 3 | за сколько дней до чистки рест закрыт |

Числовые значения читаются через хелпер, который при мусоре в БД возвращает
дефолт (настройку правит человек руками, ронять бота из-за опечатки нельзя).

`REST_MAX_DURATION` (366 дней) остаётся верхней технической границей парсера
срока; фактический предел задаёт `rest_max_days`.

### Настройка из бота

Один раздел главного меню админки — «🌴 Настройки реста» (`AdminStates.menu_rest`),
а не пункт в «Текстах сообщений» плюс отдельные лимиты: памятка и лимиты — это
одна тема, и разносить их по двум экранам значит заставлять админа помнить, где
что лежит.

- Кнопка «📝 Памятка о ресте» — показывает текущий текст и плейсхолдеры,
  принимает новый; «-» возвращает текст по умолчанию (очисткой настройки, а не
  записью дефолта в базу — иначе правка `DEFAULT_REST_TEMPLATE` в коде до
  сброшенных чатов не доедет).
- По кнопке на каждый лимит, текущее значение прямо на кнопке
  («⏳ Макс. срок: 14», «🧹 Дата чистки: не задана», «выкл.» для нуля) — отдельный
  экран со сводкой не нужен. Какой лимит правится, лежит в данных состояния
  (`REST_LIMIT_FIELDS`).
- «Отмена» из ввода возвращает в меню реста, а не в главное: лимиты обычно
  правят подряд.

### Настройка из панели

Ключи добавляются в `ALLOWED_SETTING_KEYS` (`webpanel/app.py`). Панель сейчас
принимает любую строку, поэтому появляется серверная валидация: числовые ключи —
целое от 0 до 3650, `rest_cleanup_date` — `ДД.ММ.ГГГГ` или пусто. Невалидное
значение — `HTTPException(400)` с понятным текстом.

Разбор числа живёт в `rest_rules.parse_days_setting` — им проверяют ввод и
панель, и личка бота. Иначе «14 дней» отвергалось бы в одном входе и молча
превращалось в дефолт в другом: бот на мусор в колонке берёт значение по
умолчанию, и владелец остался бы уверен, что настроил одно, а работает другое.
Функция намеренно не принимает юникод-цифры, которые `int()` разберёт, а
человек в настройке не опознает.

## 4. Проверки в потоке заявки

Все три входа (команда в группе, команда в личке, кнопочный флоу «🌴 Рест»)
сходятся в `_process_rest_request()` — проверки ставятся туда, после разбора
срока и до `db.add_rest_request`. При нарушении заявка не создаётся, админам
ничего не уходит, пользователь получает конкретную причину отказа.

Нужен один новый запрос в `db.py`:

```python
async def get_last_finished_rest(chat_id, user_id) -> Optional[dict]
```

— последний одобренный рест, у которого `expires_at` уже в прошлом (по нему
считается пауза).

## 5. Где показывается памятка

- **Пользователю при подаче.** К ответу «Заявка отправлена» добавляется
  отрендеренный шаблон: даты предварительные (сейчас → сейчас + срок), с
  пометкой, что точные даты появятся после одобрения.
- **Админам при одобрении.** В `confirm_rest` карточка дополняется тем же
  шаблоном с фактическими датами (момент одобрения → `expires_at`).

Формат дат — `ДД.ММ.ГГГГ ЧЧ:ММ UTC`, как в остальных сообщениях о ресте.

## 6. Тесты

`tests/test_panel_settings.py` — что панель отдаёт на правку ключи реста,
принимает валидные значения и отбивает мусор (нечисло, отрицательное, больше
предела, пустое; дата не в формате `ДД.ММ.ГГГГ`), а тексты не валидирует.

`tests/test_rest_rules.py` (pytest, без БД и сети):

- каждое правило срабатывает и даёт понятный текст отказа;
- граничные случаи: ровно 14 дней стажа, ровно день окончания паузы, первый и
  последний день окна перед чисткой;
- отсутствие данных (нет стажа, нет прошлого реста, нет даты чистки) не блокирует;
- `render_rest_template`: подстановка всех полей, пустая причина, экранирование
  HTML, неизвестный плейсхолдер в шаблоне не ломает рендер.

Существующие тесты панели не затрагиваются.

## Границы

- Не реализуется сама «чистка» — бот только знает её дату из настройки.
- Настройки глобальные (как остальные настройки бота), не по чатам.
- Правки только в распакованной папке `tg/`; `tg.zip` не трогаем.
