# Реальные аккаунты участников + привязка админов к тг

Дата: 2026-07-24
Статус: одобрено пользователем в чате, ожидает записи в план реализации.

## Контекст

Пятый подпроект в очереди (после «Награды — пороги по ролям», «Предложить
действие», «Нью: known_users/current_users», и мелкой правки «степень 1
наград доступна всем» — см. соседние спеки/планы в этой же директории).

Сейчас на сайте (`webpanel/`) две принципиально разные роли аккаунтов:

- **Персонал** (`owner`/`admin`) — постоянный аккаунт: `username` +
  `password_hash`, создаётся владельцем вручную (`POST /api/users`) или
  один раз при первом запуске (`POST /api/setup`). Поле `tg_user_id`
  существует в таблице (`panel_users.tg_user_id`, добавлено миграцией,
  `db.py:6461-6471`), но НИЧЕМ не заполняется для этой роли — ни одного
  эндпоинта/UI для этого нет, только прямой SQL.
- **Участник** (`member`) — временный доступ: `password_hash IS NULL`,
  пользователь пишет боту «сайт» в личке → получает одноразовый код на 10
  минут (`bot.py`, `cmd_site_code`, таблица `panel_link_codes`) → вводит на
  сайте (`POST /api/member/login`) → заводится (или переиспользуется, если
  уже был) постоянная строка `panel_users(role='member', tg_user_id=...)`.
  Сама строка не истекает, но входить можно только через новый код каждый
  раз — постоянного логина/пароля у участника нет.

Доступ к member-фиче (`Depends(auth.require_member)`, `webpanel/auth.py`)
проверяет буквально `role == 'member'` — наличие `tg_user_id` роли не
меняет. Поэтому даже если бы у админа стоял `tg_user_id`, member-эндпоинты
ему всё равно недоступны. Фронтенд (`app.js`, `if (me.role === "member")
showMember(); else showApp();`) тоже жёстко переключает один из двух
экранов целиком, никогда оба сразу.

## Требование

1. Участник получает **постоянный логин+пароль** вместо одноразового кода
   (сам код больше не нужен обычным участникам вообще) — задаётся через
   пошаговый диалог в личке боту. Дальше вход на сайт — обычный, как у
   персонала.
2. Пароль хранится **только как хэш** (та же схема, что уже используется
   для персонала) — бот физически не может «напомнить» старый пароль, а
   команда «забыл пароль» — это задать новый (тот же диалог заново). Логин
   бот может напомнить без проблем (не секретный).
3. Админ/владелец может **привязать свой существующий аккаунт** к своему
   тг — самостоятельно, будучи уже вошедшим на сайте, вводом кода,
   сгенерированного той же существующей командой «сайт». Привязка — один
   раз, «навсегда» (без отдельной функции отвязки).
4. После привязки у персонала появляются **все те же member-фичи**
   (~25 эндпоинтов `/api/member/*` — отношения/брак, кланы, питомцы, дети,
   свои награды/варны, РП-действия, предложение брака и т.д.) — под своим
   же tg-аккаунтом, дополнительно к своей админ-панели, а не вместо неё.

## Дизайн

### 1. Участник: постоянный логин/пароль вместо кода

**Бот, личка, новая команда (условно «аккаунт»)** — пошаговый FSM-диалог
(по образцу существующих FSM-меню в `AdminStates`, например ростер жалоб):

1. Проверка: если у этого `tg_user_id` уже есть строка `panel_users` с
   ролью `admin`/`owner` — отказ («вы уже привязаны как персонал, чтобы
   поменять пароль персонала используется другой процесс», без создания
   дублирующей `member`-строки для того же tg).
2. `waiting_account_username` — бот просит логин, участник отвечает. Если
   логин занят кем-то другим (сравнение без учёта регистра) — просит
   другой.
3. `waiting_account_password` — бот просит пароль. Сразу после ответа:
   `bot.delete_message(chat_id, message_id)` (удаляет сообщение с
   открытым текстом пароля из истории чата — единственный момент, когда
   пароль вообще где-то виден в виде текста), хэширование, запись/
   обновление `panel_users(role='member', username, password_hash,
   tg_user_id, tg_full_name)` — INSERT, если строки для этого `tg_user_id`
   с ролью `member` ещё нет, иначе UPDATE (одна и та же команда — и
   первичная настройка, и смена пароля/логина, и ответ на «забыл
   пароль/логин»).
4. Отдельная лёгкая команда («мой логин») — напоминает только логин (не
   пароль) по `tg_user_id`, если аккаунт уже есть.

Вход на сайт для участника дальше — **тот же существующий** `POST
/api/login` (username+password), что и у персонала — никакого отдельного
member-логина не остаётся. Старый code-based `POST /api/member/login`
можно оставить нетронутым (используется кодом на 10 минут, никак не
пересекается с новым способом) — явно не в рамках этой задачи его убирать,
раз он не мешает.

### 2. Персонал: самостоятельная привязка к тг через существующий код

Существующий флоу (команда «сайт» в личке → `panel_link_codes`, 10 минут/
один раз) **не меняется** — просто получает новый способ потребления кода.

Новый эндпоинт **`POST /api/link-telegram`** (`Depends(auth.require_user)`
— доступно и admin, и owner):
- Тело: `{code}`.
- `db.consume_panel_link_code(code)` (существующая функция) — если код
  невалиден/истёк — 400.
- Если у ТЕКУЩЕГО (уже вошедшего) аккаунта персонала `tg_user_id` уже
  установлен — 409 («уже привязан»), повторная привязка не даёт
  перезаписать существующую.
- Если тот же `tg_user_id` уже привязан к ДРУГОМУ аккаунту персонала —
  409 (нельзя привязать один тг к двум админ-аккаунтам). Эта проверка
  дублируется на уровне схемы: миграция добавляет `UNIQUE INDEX` на
  `panel_users.tg_user_id` (MySQL считает каждый `NULL` отдельным
  значением, так что это не мешает множеству ещё не привязанных строк
  персонала с `tg_user_id IS NULL`) — так что даже гипотетическая гонка
  запросов не создаст двух строк с одним и тем же `tg_user_id`.
- Иначе — `UPDATE panel_users SET tg_user_id=..., tg_full_name=... WHERE
  id = <текущий вошедший>` (новая функция в `db.py`), лог действия.

На сайте — небольшой блок в интерфейсе персонала (например, в разделе
профиля/настроек): если `tg_user_id` не установлен — поле «код из бота» +
кнопка «Привязать»; если уже установлен — просто показывает «✅ Привязан к
Telegram: {tg_full_name}», без кнопки отвязки.

### 3. Общие member-фичи для привязанного персонала

`webpanel/auth.py`, `require_member` — меняется САМА логика (не заводим
отдельную вторую функцию, чтобы не трогать все ~25 мест, где она уже
используется как зависимость):

```python
async def require_member(request: Request) -> PanelUser:
    user = await current_user(request)
    if user is None:
        raise HTTPException(401, "Нужен вход")
    if user.is_member:
        return user
    if user.role in STAFF_ROLES and user.tg_user_id is not None:
        return user
    raise HTTPException(403, "Раздел для участников")
```

Поскольку все `/api/member/*`-хендлеры и так работают через
`user.tg_user_id` из сессии (комментарий в коде: «ВСЁ — только за себя»),
сами тела ~25 эндпоинтов не меняются вообще — меняется только то, кого
пускает сама проверка.

**Фронтенд** — `app.js`, текущее жёсткое `if (me.role === "member")
showMember(); else showApp();` заменяется на: персонал всегда видит
`showApp()` по умолчанию; если у персонала есть `tg_user_id` — в навигации
появляется дополнительный пункт («Мой профиль участника»), который
переключает вид на `showMember()`-экран (тот же самый, что видит обычный
участник) и обратно — это ДОПОЛНИТЕЛЬНАЯ вкладка, а не замена всего
интерфейса. Чистый участник (`role === 'member'`) продолжает видеть только
`showMember()`, как и сейчас — для него ничего не меняется.

## Не в рамках (сознательно не делаем)

- Не удаляем существующий code-based `POST /api/member/login` — оставляем
  как есть, он не мешает новому способу и не запрашивался к удалению.
- Не делаем отвязку тг для персонала (только владелец может поправить
  вручную в БД, если понадобится) — соответствует «навсегда».
- Не меняем `POST /api/setup`/`POST /api/users` (создание персонала
  владельцем) — привязка тг для них происходит отдельным шагом уже после
  создания аккаунта, самим владельцем аккаунта.
- Не добавляем anti-bruteforce для нового `POST /api/link-telegram` сверх
  того, что уже даёт сам код (10 минут, одноразовый, привязан к
  конкретному `tg_user_id`) — сочтено достаточным на этом этапе.

## Тесты

- Новые тесты бота (диалог «аккаунт»): создание нового member-аккаунта,
  смена пароля/логина существующего, отказ при попытке создать
  дублирующий аккаунт для уже привязанного персонала, удаление сообщения с
  паролем, напоминание логина.
- Новые тесты панели: `POST /api/link-telegram` — успешная привязка,
  отказ на уже привязанный аккаунт (свой и чужой), невалидный/просроченный
  код.
- Обновление `require_member`: тест, что персонал с привязанным
  `tg_user_id` проходит на `/api/member/*`, персонал без привязки — нет,
  участник (`role=member`) — как и раньше, проходит.
- Ручная проверка (описать в плане, не автоматизировать): фронтенд-
  переключение между админ-панелью и профилем участника у одного и того
  же привязанного персонала-аккаунта.
