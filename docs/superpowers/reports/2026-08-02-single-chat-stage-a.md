# Этап А: сделано, и что осталось запустить

Дата: 2026-08-02

## Решение владельца

Данные к чатам не привязаны вовсе. Всё — люди, позывные, муты,
сообщения, экономика, игры — принадлежит ОДНОМУ рабочему чату.
Второй чат нужен только как адрес: уведомления админам и переписка с
теми, кто просится войти. Своих данных у него нет.

## Сделано (всё обратимо)

1. `chats.py` — единственный источник правды о чатах.
2. Кабинет пускает только рабочий чат.
3. Семнадцать эндпоинтов не принимают `chat_id` — чат знает сервер.
4. С девяти экранов ушёл выбор чата.
5. Скрипты: дамп, отчёт по чатам, классификатор, миграция.

## Классификация: колонка уходит из 100 таблиц

Исключений нет. `settings` в список не попала и попасть не может:
там `notify_chat_id` и `complaint_chat_id` — это ЗНАЧЕНИЯ, адреса
чатов, а не разделение строк.

## Что делает миграция при совпадении ключей

Ключ у большинства таблиц составной: `(chat_id, user_id)`. Убери из
него чат — и две строки одного человека из разных чатов становятся
одной. Правило: **побеждает строка рабочего чата**. Проигравшие не
пропадают — уходят в `migration_losers_<дата>.sql`, откуда их можно
прочитать и вернуть руками.

## Запустить на сервере

```bash
bash tools/backup_db.sh                              # дамп ДО всего
.venv/bin/python -m tools.chat_report                 # кто где лежит
.venv/bin/python -m tools.migrate_drop_chat_id        # холостой прогон
.venv/bin/python -m tools.migrate_drop_chat_id --выполнить
```

Миграция откажется работать без дампа моложе суток: DROP COLUMN
необратим, и вернуть данные больше нечем.

## После миграции

Схема и код разъедутся: в таблицах колонки уже нет, а `db.py` всё ещё
шлёт её в каждом запросе. Это план Б (этапы 5-6) — правка `db.py`,
четырёх тысяч вызовов и тестов. Пишется отдельно и выполняется сразу
после миграции, иначе бот не поднимется.
